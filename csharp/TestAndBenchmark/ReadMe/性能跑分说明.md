# 性能跑分说明

## 一、性能跑分测量什么

性能跑分用于比较不同锁策略在相同业务负载、线程数量和读写比例下的吞吐量、CPU 使用效率与扩展性。

标准跑分会横向测试：

- `lock`；
- `ReaderWriterLockSlim`；
- `ConcurrentExclusiveLock`。

性能测试回答的是：

> 在同一组测试条件下，每种锁能够完成多少业务 Work，以及为这些吞吐量付出了多少时间和 CPU。

性能结果不能替代语义正确性测试。只有先通过语义测试，性能数据才具有讨论价值。

---

## 二、测量原理

每种锁策略、每个读写场景都会创建独立的锁实例和独立的 Work 数据，不复用其他锁已经运行过的业务对象。

正式计时前会执行预热。专用 Thread 创建完成并到达 ready 屏障后，主线程才开始计时并统一打开 start gate，因此线程创建和准备阶段不计入成绩。

每次程序运行只加载 `--workload` 指定的一种 Work，但会自动测试全部锁策略和以下读写比例：

```text
100 / 0
99.5 / 0.5
90 / 10
50 / 50
30 / 70
0 / 100
```

每次成功获得权限后：

- 读操作执行 `TickRead`；
- 写操作执行 `TickWrite`；
- `--read-work` 和 `--write-work` 控制对应方向的业务步骤数。

测试使用专用 `Thread`，不同锁策略分轮执行，不会把多种锁混在同一个计时区间。

---

## 三、核心运行参数

| 参数 | 含义 |
|---|---|
| `--lock-instances` | 同一策略同时运行的独立“锁 + Work”实例数量，默认值为 1。 |
| `--threads` | 每个锁实例拥有的专用 Thread 数量。 |
| `--operations` | 每个线程执行的锁获取和业务 Work 次数。 |
| `--workload` | Work 类型：`cpu`、`memory`、`dictionary`、`ledger` 或 `payload`。 |
| `--work` | 同时设置读和写的业务步骤数。 |
| `--read-work` | 每次读操作的业务步骤数，覆盖 `--work` 的读方向。 |
| `--write-work` | 每次写操作的业务步骤数，覆盖 `--work` 的写方向。 |
| `--memory-mb` | `memory` 工作集每个锁实例使用的内存大小，单位 MiB。 |
| `--dictionary-size` | `dictionary`、`ledger` 和 `payload` 每个锁实例使用的数据规模。 |

总线程数和总锁操作数为：

```text
总线程数   = lock-instances × threads
总锁操作数 = lock-instances × threads × operations
```

例如：

```text
--lock-instances 4 --threads 32 --operations 10000
```

表示：

- 创建 4 个独立锁和 4 份独立 Work；
- 每把锁拥有 32 个专用线程；
- 总线程数为 128；
- 总锁操作数为 1,280,000。

`--memory-mb` 和 `--dictionary-size` 都按每个锁实例解释。增加 `--lock-instances` 时，总数据规模也会按实例数增长。

## 四、Work 类型

### `cpu`

以整数计算为主，极少访问大数据结构。

适合观察：

- 锁本身的常态开销；
- 短临界区吞吐；
- 线程数量增加后的竞争成本；
- 不同业务步骤数下的性能交叉点。

`--work 0` 仍会保留必要的接口调用和最小状态访问，不是完全空方法。

### `memory`

对大共享数组进行随机访问。

适合观察：

- CPU 缓存影响；
- 内存带宽；
- NUMA；
- 多锁实例扩大工作集后的变化。

### `dictionary`

执行字符串键字典查询、对象访问和缓存更新。

适合模拟对象缓存、索引表和共享字典业务。

### `ledger`

执行账户查询、余额校验、转账和审计记录。

适合模拟分支较多、读取和状态修改混合的实体业务。

### `payload`

执行二进制报文头解析、条件判断和字段原位更新。

适合模拟网络协议、消息处理和二进制状态更新。

不同 Work 的一次操作复杂度不同，不能直接用 `works/s` 在不同 Work 之间横向排名。

## 五、结果指标

程序输出中的常见指标包括：

| 指标 | 含义 |
|---|---|
| `elapsed` | 当前锁策略和读写场景完成全部操作所用的时间。 |
| `cpu%` | 根据计时区间内的进程 CPU 时间估算出的 CPU 使用率，用于辅助观察资源消耗趋势。 |
| `works/s` | 全部锁实例每秒完成的 `TickRead` 与 `TickWrite` 总数。 |
| `works/s/lock` | `works/s` 除以锁实例数量，表示平均每把锁的吞吐量。 |
| `work/cpu%` | `works/s` 除以 CPU 使用百分比，用于观察单位 CPU 对应的吞吐效率。 |
| `reads` / `writes` | 实际完成的读 Work 和写 Work 数量。 |
| `state` | Work 最终共享状态摘要，用于检查不同锁策略的业务结果是否一致。 |

### 关于 `cpu%` 的说明

`cpu%` 来自计时区间内的进程 CPU 时间采样，不是硬件级精确测量值。

它会受到计时区间长度、系统调度、后台负载、线程迁移、CPU 动态频率以及计时精度影响。测试时间很短时，数值可能明显波动，甚至出现 0 或短暂异常偏高，因此不应根据几个百分点的细小差异下结论。

不过，在同一台机器、相同参数、足够长的计时区间下重复测试时，`cpu%` 仍然具有参考价值，可以辅助判断：

- 某种锁策略是否明显占用更多 CPU；
- 吞吐量提升是否伴随更高的 CPU 消耗；
- 多锁或高线程配置下的资源使用趋势；
- `work/cpu%` 所反映的单位 CPU 吞吐效率。

`work/cpu%` 由 `works/s` 和 `cpu%` 计算得到，因此同样只能作为辅助指标。正式比较应以 `elapsed`、`works/s`、结果一致性和多次重复运行的稳定区间为主。

结果应满足：

```text
reads + writes = lock-instances × threads × operations
```

同一个 Work、同一个读写比例、同一组参数下，不同锁策略的 `state` 应一致。出现 `final work state differs` 等警告时，该轮性能数据不应作为有效结论。

---

## 六、如何正确比较结果

1. 只比较同一个 Work、同一个读写比例和同一组参数下的不同锁策略。
2. 不同 Work 的业务复杂度不同，不应直接按 `works/s` 排名。
3. 单锁结果适合观察同一共享对象上的竞争；多锁结果适合观察大量独立实体同时运行时的聚合吞吐。
4. `--threads` 表示每把锁的线程数，不是全进程线程数。
5. 多锁实例时，必须同时关注 `works/s` 和 `works/s/lock`。
6. 正式测试不要挂调试器，应使用准备好的 Release 发布包。
7. 尽量关闭其他高负载程序，避免系统调度和后台负载干扰结果。
8. 正式结论应重复运行多次，观察稳定区间，不使用单次最高值。
9. 单个场景最好至少持续 1 秒；正式对比建议达到 3 秒以上。
10. `cpu%` 和 `work/cpu%` 只用于辅助观察明显趋势，不应比较细小差异。
11. 毫秒级冒烟配置只用于验证程序流程，不能用于评价 CPU 效率或锁性能。

---

## 七、高级权限路径性能对照

`--advanced-perf` 只测试 `ConcurrentExclusiveLock` 的高级权限路径，不参与 `lock` 和 `ReaderWriterLockSlim` 的标准横向排名。

它用于比较同规模下不同 CEL 调用路径的成本，例如：

- 普通 Concurrent；
- Exclusive 降级到 Concurrent；
- 普通 Concurrent 与降级后 Concurrent 的混合路径；
- 普通 Exclusive；
- Concurrent 条件升级到 Exclusive；
- 普通 Exclusive 与 Concurrent → Exclusive 升级的混合路径。

所有输出使用相同的线程数、每线程操作数和业务步骤数，因此适合观察不同权限流程本身的相对成本。

## 八、直接运行命令

```powershell
# 查看全部命令行选项
.\TestAndBenchmark.exe --help

# 快速冒烟：只确认程序可以完整运行
.\TestAndBenchmark.exe --lock-instances 1 --threads 4 --workload cpu --operations 100 --work 4

# 接近锁自身开销：短临界区
.\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload cpu --operations 100000 --work 0

# 极短CPU业务
.\TestAndBenchmark.exe --lock-instances 1 --threads 16 --workload cpu --operations 100000 --read-work 64 --write-work 128

# 加重锁内业务
.\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload cpu --operations 100000 --read-work 256 --write-work 256

# 短随机访存
.\TestAndBenchmark.exe --lock-instances 1 --threads 32 --workload memory --operations 10000 --memory-mb 64 --read-work 32 --write-work 32

# 大工作集随机访存
.\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload memory --operations 10000 --memory-mb 64 --read-work 64 --write-work 128

# 字典缓存业务
.\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload dictionary --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128

# 账户、转账与审计业务
.\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload ledger --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128

# 多锁实例：4 把锁，每把锁 32 个专用线程
.\TestAndBenchmark.exe --lock-instances 4 --threads 32 --workload ledger --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128

# 随机访存多锁
.\TestAndBenchmark.exe --lock-instances 100 --threads 8 --workload memory --operations 1000 --memory-mb 16 --read-work 128 --write-work 128

# 多锁字典
TestAndBenchmark.exe --lock-instances 100 --threads 16 --workload dictionary --operations 1000 --dictionary-size 1280 --read-work 64 --write-work 64

# CEL 高级权限路径性能对照
.\TestAndBenchmark.exe --advanced-perf --threads 64 --operations 100000 --work 64
```
