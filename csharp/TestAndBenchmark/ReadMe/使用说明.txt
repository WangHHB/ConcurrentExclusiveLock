LockBenchmark 使用说明
======================

一、运行要求
------------

1. 在 TestAndBenchmark.exe 所在目录执行命令。
2. 测试机器只运行已经准备好的 ReleaseClient 发布包，不需要源码或编译工具。
3. 普通框架依赖发布需要复制整个输出目录，并确保测试机器安装 .NET 8 Runtime；只有单文件发布才能只复制 EXE。
4. 正式测试时不要挂调试器，并尽量关闭其他高负载程序。
5. 每次程序运行只加载 --workload 指定的一种 Work，但会自动测试全部读写比例和全部锁策略。
6. 文档中的 EXE 命令均使用单行格式，可直接粘贴到 cmd.exe 或 PowerShell。
7. 包含 foreach 的批量示例仅适用于 PowerShell。
8. --lock-instances 默认为 1；大于 1 时，每种策略会创建对应数量的独立“锁 + Work”实例。

查看命令行帮助：

    .\TestAndBenchmark.exe --help


二、四个核心参数
----------------

--lock-instances
    同一策略同时运行的独立单锁案例数量，默认值为 1。
    lock、ReaderWriterLockSlim、ConcurrentExclusiveLock 等会分轮各自创建 N 个实例。

--threads
    每个锁实例各自拥有的专用 Thread 数量。

--operations
    每个线程获取锁并执行一次业务 Tick 的次数。

--work
    每次成功获取锁后，在锁内执行的业务步骤数。
    它同时设置 TickRead 和 TickWrite 的步骤数。

关系：

    总线程数   = lock-instances × threads
    总锁操作数 = lock-instances × threads × operations

示例：

    --lock-instances 4 --threads 32 --operations 10000 --work 256

含义：

1. 创建 4 个独立锁和 4 个独立 Work。
2. 每把锁各有 32 个专用工作线程，共创建 128 个线程。
3. 每个线程执行 10000 次锁获取和业务 Tick。
4. 每次进入锁内后执行 256 个业务步骤。
5. 总计约 1280000 次锁操作。

读写业务量也可以分别设置：

    --read-work 64 --write-work 256

--read-work 或 --write-work 会覆盖 --work 对应方向的值。

容量参数只要求大于 0，不设置人为上限：

    --memory-mb
    --dictionary-size

实际可用上限由 .NET 集合/数组限制、进程位数和测试机器可用内存决定。
memory-mb 和 dictionary-size 都按“每个锁实例”解释，总数据规模约等于单实例规模乘以 lock-instances。
超大工作集会为每种锁和每个场景重新创建，初始化时间虽然不计入单项成绩，但会显著增加整轮测试耗时。


三、自动执行的读写比例
----------------------

每条命令都会自动执行以下场景：

    read/write 100/0
    read/write 99.5/0.5
    read/write 90/10
    read/write 50/50
    read/write 30/70
    read/write 0/100

当前没有单独选择某个比例的命令行参数。


四、预热和计时边界
------------------

1. 正式测试前会用 lock-instances=1 的缩小配置预热所选 Work 和全部锁策略。
2. 预热 Work 与正式测试 Work 完全分离，预热结束后会执行 GC 回收。
3. 每种锁、每个正式场景都会重新 new 一个 IWork 并调用 Init。
4. 不会复用其他锁运行过的数组、字典或业务对象。
5. 专用 Thread 的创建和到达 ready 屏障不计入测试时间。
6. 全部线程就绪后，主线程开始计时并统一打开 startGate。


五、常用命令
------------

1. 快速冒烟测试

    .\TestAndBenchmark.exe --lock-instances 1 --threads 4 --workload cpu --operations 100 --work 4

用途：确认程序能够完整运行、没有异常或状态不一致警告。


2. 接近纯锁自身开销

    .\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload cpu --operations 100000 --work 0

work=0 仍会保留最小状态读取/更新和接口调用，不是完全空方法。


3. 锁内工作量梯度

    $steps = 0,1,4,16,64,256

    foreach ($step in $steps) {
        .\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload cpu --operations 100000 --work $step
    }

用途：观察不同锁随着临界区变长发生性能交叉的位置。


4. 大工作集随机访存

    .\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload memory --operations 10000 --memory-mb 64 --read-work 64 --write-work 128


5. 字典与对象缓存业务

    .\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload dictionary --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128


6. 账户、转账与审计业务

    .\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload ledger --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128


7. 二进制报文解析与更新

    .\TestAndBenchmark.exe --lock-instances 1 --threads 64 --workload payload --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128


8. 读写单次成本模型

对称成本：

    --read-work 256 --write-work 256

读操作更重：

    --read-work 1024 --write-work 256

写操作更重：

    --read-work 256 --write-work 1024

注意：实际业务 Work 的 TickWrite 通常包含更多分支和状态修改，因此步骤数相同不代表 CPU 成本完全相同。


9. 双路服务器线程梯度

    $cpu = [Environment]::ProcessorCount
    $threadCounts = @(1, [Math]::Max(1, [int]($cpu / 2)), $cpu, $cpu * 2)

    foreach ($threadCount in $threadCounts) {
        .\TestAndBenchmark.exe --lock-instances 1 --threads $threadCount --workload ledger --operations 10000 --read-work 64 --write-work 128
    }

用途：分别观察单线程、半机、全机和超额订阅下的扩展性与调度代价。


10. 多锁实例

    .\TestAndBenchmark.exe --lock-instances 4 --threads 32 --workload ledger --operations 10000 --dictionary-size 65536 --read-work 64 --write-work 128

含义：每轮创建 4 个同类型锁和 4 个独立 LedgerWork，每把锁各有 32 个固定竞争线程，共 128 个专用线程。
不同策略仍然分轮测试，不会把 lock、ReaderWriterLockSlim 和 ConcurrentExclusiveLock 混在同一个计时区间。
总线程数等于 lock-instances × threads；数值过大时，准备 OS Thread 会很慢甚至因系统资源不足而失败。


六、Work 类型
-------------

cpu
    极少访存、纯整数运算，适合观察锁本身开销。

memory
    大共享工作集随机访存，用于放大缓存、NUMA 和内存带宽影响。

dictionary
    字符串键 Dictionary、对象跳转、缓存查询与更新。

ledger
    账户查询、余额校验、转账和审计记录。

payload
    二进制报文头解析、条件判断和原位字段更新。


七、结果判读
------------

works/s
    整轮全部锁实例每秒完成的 TickRead 与 TickWrite 总数。越高表示聚合吞吐量越高。

works/s/lock
    works/s 除以 lock-instances，表示平均每个锁实例的每秒 Work 数。

work/cpu%
    works/s 除以 CPU 使用百分比，用于观察单位 CPU 占用对应的吞吐效率。
    此效率不除以 lock-instances；平均单锁的 works/s 和 cpu% 会同时除以实例数，两者相除后实例数抵消。

reads / writes
    实际完成的读 Work 和写 Work 数量。

state
    IWork 最终共享状态摘要，以固定 16 位十六进制显示；它完整保留 long 的 64 位状态，便于定宽对齐和逐行比较。

检查项：

1. reads + writes 应等于 lock-instances × threads × operations。
2. 不应出现 final work state differs 警告。
3. 只能直接比较同一个 Work、同一个读写场景下的不同锁结果。
4. 不同 Work 的一次 Tick 复杂度不同，不应直接按 works/s 横向排名。
5. 正式结论建议重复运行多次，观察稳定区间，不使用单次极值。
6. cpu% 和 work/cpu% 依赖进程 CPU 时间采样。单个场景的 elapsed 至少应达到 1 秒，正式测试建议达到 3 秒以上。
7. --operations 100 --work 4 这类毫秒级配置只适合检查线程、计数和 state；此时 CPU 时间分辨率不足，cpu% 可能为 0 或短暂超过 100%，不应据此评价性能。


八、高级锁功能
--------------

IAdvancedLockFunctions 是独立功能测试模块，不进入标准锁横向排名。

运行阶段3高级语义正确性测试：

    .\TestAndBenchmark.exe --advanced-correctness

追加大量独立锁并发测试：

    .\TestAndBenchmark.exe --advanced-correctness --lock-instances 1000 --advanced-operations 4

--lock-instances 指定独立锁数量。

--advanced-operations 指定每把锁、每种高级操作的基准任务轮数。
降级、收敛和升级会为每把锁分别生成随机任务量，在基准值上下约 25% 浮动；
整数取值至少为 1。每次运行会打印随机 seed，也可显式指定以复现：

    .\TestAndBenchmark.exe --advanced-correctness --lock-instances 1000 --advanced-operations 4 --advanced-seed 12345

大量独立锁模式分三批执行降级、收敛和升级；每把锁固定两个专用 Thread，
任务量增加时复用这两个线程，因此最大同时线程数始终为 lock-instances × 2，
不会沿用标准压力测试的 --threads 和 --operations 工作量。

该命令使用专用 Thread 和带超时的黑盒断言，依次验证：

1. ExclusiveToConcurrent 降级后连续保留 Concurrent，普通 Exclusive 不得插入。
2. ConvergeConcurrent 等待参与者到达及非参与读者退出，期间阻止新 Concurrent，结束后恢复正常状态。
3. TryConvergeConcurrentToExclusive 恰好一个成功，优先于普通 Exclusive，并覆盖失败自动释放、失败保留和赢家降级协议。

全部通过时退出码为 0；任一案例失败或超时时退出码非 0。

高级语义性能对照：

    .\TestAndBenchmark.exe --advanced-perf --threads 64 --operations 100000 --work 64

加重锁内业务后再看一次：

    .\TestAndBenchmark.exe --advanced-perf --threads 64 --operations 100000 --work 640

该命令只测试 ConcurrentExclusiveLock，不参与 lock、ReaderWriterLockSlim 的横向排名。
每条输出都使用相同的 threads、operations/thread，并且每个语义循环只执行一次 DoWork(work)。

当前输出包含以下同规模路径：

1. AcquireConcurrent -> DoWork -> ReleaseConcurrent
2. AcquireExclusive -> ExclusiveToConcurrent -> DoWork -> ReleaseConcurrent
3. 读侧混合路径：一半线程执行普通 Concurrent，一半线程执行 ExclusiveToConcurrent 后的 Concurrent
4. AcquireExclusive -> DoWork -> ReleaseExclusive
5. AcquireConcurrent -> TryConcurrentToExclusiveWithSwitchContextID -> DoWork -> ReleaseExclusive
6. 写侧混合路径：一半线程执行普通 Exclusive，一半线程执行 ConcurrentToExclusive 升级

阶段5全语义正确性测试：

    .\TestAndBenchmark.exe --full-semantics --lock-instances 64 --semantic-workers 4 --semantic-operations 256

参数：

    --lock-instances      随机状态机使用的独立锁数量
    --semantic-workers    每把锁的专用 Thread 数量，至少为 2
    --semantic-operations 每把锁执行的随机合法状态轮数
    --semantic-seed       可选随机种子，用于复现调用路径

阶段5首先执行全部确定性访问契约，然后执行模型驱动的随机合法路径。
随机路径只生成正确调用协议，每轮覆盖以下状态之一：普通 Concurrent、普通 Exclusive、
ExclusiveToConcurrent、ConvergeConcurrent、TryConvergeConcurrentToExclusive，
以及同一持有链反复 Exclusive -> Concurrent -> Exclusive 的权限转换环。
测试持续校验 Concurrent ID 范围及唯一性、升级唯一赢家，以及 Exclusive/Concurrent 业务权限不得重叠。

按约定，State 和 Contention 快照不属于阶段5测试范围。

长时间耐久度验证：

    .\TestAndBenchmark.exe --endurance 24h

耐久度模式只接收 --endurance 标识和测试时长。时长支持 30s、15m、24h、1d 或 hh:mm:ss。
锁数量和每锁线程数按逻辑处理器数量自动生成；同一批锁对象会存活并复用于整个测试过程。
测试持续生成六类合法调用路径，每分钟输出累计轮数、CPU、内存、GC、线程数和路径分布。
任一权限模型断言、超时或线程异常都会立即打印失败批次及随机 seed，并以非 0 退出码结束。
